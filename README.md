## v0.14.0 新增（研究文档 07 §9 里程碑 M1–M4 落地）

上一轮（v0.13.0）把 `docs/research/09` 的**四个候选方向**落地了，但 `07` 的
**里程碑 M1–M4 一条都没做**（起点实测：`risk-calibration.ts` / `risk-bayes.ts` /
`mutation.mjs` / 预防性指标全部不存在）。本轮只做这四件事，不新增无关特性。

- **M1 · 误伤反馈闭环（RQ2）** — 新增 `src/risk-calibration.ts`。
  从 journal 采集误伤样本，**严格区分证据来源**：连续 `enable` 段被 `restore`
  收尾 ⇒ 系统自动恢复（**不是**误伤证据）；否则 ⇒ 用户主动放行（是证据）。
  自适应阈值只升不降、必须有观测到的用户撤销才动、无数据不动。
  为什么这个区分是核心：把系统恢复误算成误伤，会让阈值越来越高 ——
  「因为你还没出过错所以更不信任你」。
  面板与命令窗口都能看到「本轮为何提高阈值」（不做黑盒）。

- **M2 · 贝叶斯风险评分（RQ1，并行读数）** — 新增 `src/risk-bayes.ts`。
  `Beta(1,1)` 先验 + 命中/未命中共轭更新，给出后验均值与 95% 可信区间
  （连分式 + logit 空间二分，对 8 组闭式解析解交叉验证，误差 ~1e-15）。
  **硬纪律**：绝不切换默认 `riskScore` —— 两套读数并列显示，让分歧可见。
  差异面压到最小：`recency`/`experimental` 直接复用既有实现（逐位相同），
  只把 0.2 那一项换成后验均值；有断言钉住 6 组输入下逐位相等（基线 0.4952/0.9952）。
  样本 < 3 ⇒ `defined:false` + `value:null`，不编数字。

- **M3 · 预防性健康指标（RQ3，只预警不行动）** — 新增 `src/preventive.ts`。
  `loadTimeEwma`（EWMA 控制带，带宽乘 `√(λ/(2−λ))` —— 不乘会让带宽约 3 倍、
  漂移永远报不出来）+ `configChangeCusum`（k=0.5 / h=5，取自 Page 1954 与
  Montgomery 的 ARL 表）。**只预警、零副作用、零关闭逻辑**（用逐字节比对断言钉住）。
  实现中发现并修掉两个真实检测器缺陷：MAD 在 ≥50% 同值时退化为 0（会让阶跃被
  静默判成「完全规则」）、整段尺度被待检漂移自己污染（同一夹具 S 只到 3.4 < h=5，
  改差分型移动极差后 21.86 正常越界）。两条都有回归锁。

- **M4 · 自动化变异测试（RQ4）** — 新增 `scripts/mutation.mjs`（零新依赖）。
  四类变异子（删 try/catch、换比较方向、翻 phase、改指针路径）+ 杀灭率门禁
  （`--min-kill-rate` 供 G2 消费）+ 四道恢复闸口（变异体绝不留在仓库里）。
  杀灭率从 28.9% 提升到 **47.5%**，且**归因到三类**（真实缺口 / 等价变异体 /
  工具边界），不止报一个数字。

### 为什么「47.5%」不是结论

变异测试最有价值的产出不是那个百分比，而是它抓到的三件事：

1. **2 个真缺口**：`tool-render.ts` 的 `omitted > 0` / `extra > 0` 改成 `>= 0`
   后**没有任何测试变红** ⇒「省略提示是否真的出现」从未被断言。已补测试杀死。
2. **我自己写测试的错误**：第一版用 `/省略/` 匹配文案，而真实输出是
   `其余 N 项未展开` —— 函数里没有「省略」二字。新测试全绿、变异体却存活。
3. **工具漏判**：测试用 `.ts` 后缀 import 时映射不到模块 ⇒ 那批变异体从未被评估，
   而报告只显示「无直接测试文件」。改 `.js` 后立刻 +1 杀死。

> 47.5% 不等于「测试强度 47.5%」：分母只是「工具生成的变异体」，而工具只覆盖
> 四类文本变换。本项目缺陷的主流是结构/时序类，不在这个分母里。

### 诚实边界（两条判据本轮**不能**声称达成）

07 给的 M2 判据是「Top-1 命中率提升 ≥ 5%」、M3 是「预警提前量 ≥ 1 轮」。
这两条都需要**真实崩溃/预警样本**，而本机没有。本轮交付的是**机制已就位**：
数学正确、诚实边界正确、接线可验证；**效果待真机数据**。
没有样本就说有提升，正是研究文档 05 §4 批评的「看起来绿」。

## v0.13.0 新增（研究落地：决策可解释 + 安装不崩 + 图谱读得懂结构）

本轮把 `docs/research/` 九篇研究文档里的**候选方向**逐条落地，并对每条做了
「前提核对 → 改造 → 验证」，**拒绝了三个原方案**（理由见下）。

- **决策因子快照（方向③·研究文档 09 判定为 P0）**：`decision.json` 的
  `suspects[]` 新增 `evidence` 字段，记录 `rank / risk / factors（三因子加权贡献）/
  streak / changeCount / source`。此前只记排序键（`lastChangeAt`），回答不了
  「为什么是 A 而不是 B」—— A 可能靠 experimental 拉高、B 可能靠 recency 拉高，
  总分相同但成因完全不同。没有这份快照，任何模型调参都是盲调。
  面板新增「决策因子」卡片（三因子条形分解），命令窗口 `status` 同步携带。
- **排序口径统一（研究文档 09 §5 的最大缺口）**：此前**决策路径用
  `rankByRecency`（纯时间戳）、面板展示用 `riskScore`（三因子）**—— 两套口径。
  后果是高风险的没被关、且改模型对决策完全不生效。现在确定性证据（唯一嫌疑）
  保持时间戳序（零行为变化），概率性证据（多嫌疑）按 `riskScore` 排序头号嫌疑。
- **变更频率因子（方向①·改造后落地）**：没有照搬 LRU-K —— 它的语义是「最近是否
  被频繁**访问**」，本场景要的是「最近是否被频繁**变更**」，属语义错配。改为在既有
  `riskScore` 里补频率维度，做成 recency 的**调制乘数**：`recency × (1 + α·density)`，
  α=0.5、cap=5。为什么不是第四个加法因子：三因子权重之和恰为 1，加一项要么破坏
  归一化、要么重分配权重（既有断言集体失效、旧决策不可比）。约束：频率不能压过
  时间局部性（有断言钉住「一个月前的高频插件仍低于一小时前的单次插件」）。
- **分布形态阈值（方向②·拒绝原方案）**：原提议是「证据年龄指数衰减」。**拒绝**：
  `confirmRounds` 的语义是「同一头号嫌疑连续复现」，而 `environmentChanged` 已保证
  环境没变——环境没变时的复现无论间隔多久都是该插件的缺陷，加时间衰减会判成
  证据不足 ⇒ **放过真缺陷**，违反「宿主可用性优先于误伤最小化」。改用已有的
  Weibull 形状 k（零新模型）：k<0.9 成簇 ⇒ 阈值下调 1；k>1.1 趋于规则 ⇒ 上调 1；
  样本不足/撞搜索上界 ⇒ 不动。幅度只有 ±1，兜底升级不受影响。
- **共现信号（方向④·只验证不加权）**：**拒绝**直接加权——数据基础不存在
  （项目没有插件间运行时依赖图）、共现 ≠ 因果（会增加误伤）、且不可证伪。
  改为只做采集 + 验证：`verifyCooccurrence` 算「官方实验插件活跃侧 vs 不活跃侧
  的命中率差」，`mayWeightByCooccurrence` 是**门**（差值达标 **且** 每侧样本 ≥10）。
  诚实边界：样本不足 ⇒ `undefined`，绝不说成「无差异」（那会给「共现无用」提供伪证据）。
- **安装不崩（P0·沙箱实测发现的真缺陷）**：`@deepseek-ai/schemastery` 与
  `@deepseek-ai/dsh-tools` 是 `optional: true` 的 peer，但产物里是**静态 ESM import** ——
  宿主没暴露它们时**整个插件加载失败**（不是功能降级，是 require 就崩）。对守护插件
  尤其致命：它恰恰要在「宿主环境不完整」时还能加载。改为惰性解析 + 诚实降级
  （schemastery 缺失 ⇒ 纯对象 schema，8 字段齐全带默认值；dsh-tools 缺失 ⇒ 原样注册
  并打 `degraded` 标记）。沙箱 `sb-rg-c11` 实测加载成功。
- **图谱结构洞察（用户原话「功能还很贫乏」）**：新增 `graph-analysis.ts`（纯函数，
  O(V+E)）：度数 + 角色判定（source/sink/hub/isolated）、正向可达、反向影响面、
  最短因果链。面板图谱区新增结构条，可点击 chip 直达节点，色块之外附可读句子
  （灰度/色盲可读）。枢纽用度数排序而非中介数中心性（后者 O(V·E)，20~60 节点下
  收益不抵复杂度）。
- **命令窗口显示复原**：`formatStatus` 渲染决策因子三因子分解；顺手修了一个真实
  健壮性缺口——畸形条目在 `.toFixed` 抛异常会吞掉整张卡片 ⇒ 数值兜底，钉住
  「`render` 是全函数」。

# dsh-recency-guard

**插件崩溃恢复守护** —— 解决"添加或更新第三方/实验性插件导致 DSH 崩溃、必须禁用所有插件再逐个添加"的问题。

当某个插件把 DSH 拖垮时，本插件会在崩溃的那一刻记录下"谁最可疑"，并在**下一次启动时、在崩溃插件的代码被加载之前**把它挡在门外。反复崩溃时，关闭的插件会逐个增加（第 1 次关最近更新的 1 个，仍崩溃则关最近更新的 2 个）。稳定之后，除首要嫌疑外，其余被关闭的配置会自动恢复。

## v0.12.1 修复（两条均由真机用户旅程发现）

- **崩溃信号补第二条通道（P0 检测缺口）**：崩溃信号此前**只有哨兵文件**，而哨兵写在
  `process.on('exit')` 里 —— SIGKILL / OOM killer / 断电 / 原生段错误**根本不运行
  exit 处理器**。真机实测：强杀后 `bootMarker` 残留（pid 已死）而 `crashSeq` 仍是 0，
  下一次启动报「启动时未发现上次崩溃」。
  危险的不是少记一次，而是**崩溃循环失去升级依据**：插件以原生方式撞死宿主时，
  每一轮都只看到残留标记、每一轮都被当成干净启动清零计数 ⇒ 永远停在「关 0 个」。
  新增 `classifyAbnormalExit` 四种结局：
  - `clean`（无残留 / 有哨兵）⇒ 归零；有哨兵时走既有通道、**不重复计数**；
  - `self-reload`（残留 pid == 本进程，热重载/HMR）⇒ 归零 + 留痕；
  - `concurrent`（残留 pid 仍活着且不是自己）⇒ 归零 + 留痕「另一个实例在运行」；
  - `abnormal`（残留 pid 已死）⇒ 计数 +1，累计到 `confirmRounds` 才动手。
  异常终止按**概率性证据**处理（残留标记也可由人为杀进程/关机产生）：第 1 轮只观察、
  第 2 轮才行动，达阈值后复用既有 `recover()` 通道关闭（不另写一套关闭逻辑，
  避免两条通道的隔离语义各自漂移）。真机两次强杀验证：
  `1/2 轮 act=false` → `2/2 轮 act=true 关闭 1 个`。
  顺带修了引出它的二阶缺陷：原 `recovering && !crashedLastRun` 把「没有哨兵」
  当「活过了启动」的代理，新通道下异常终止同样没有哨兵 ⇒ 会把「关了嫌疑 → 又死一次」
  读成「崩溃已过」而恢复全部插件，亲手拆掉刚建立的隔离。现改为要求
  `exitClass === 'clean'`，并拆成纯函数 `shouldRestoreAfterBoot` 用 5 条单测钉住。
- **小地图点击无反应（真机 GUI 实测）**：`setPointerCapture?.(id)` 排在
  `onNavigate(...)` **之前**，而可选链只保护「方法不存在」、**不保护方法抛异常**。

  否决了「定位到那一块」这个主功能。
  修法：捕获/释放各自 `try` 包裹并抽成 `capturePointer`/`releasePointer`；
  新增 3 条**源码门**（`minimap-gesture.test.ts`）钉住「不得出现裸调用」，
  并经**变异自证**会响（写回裸调用 ⇒ 恰 1 条断言 FAIL）。真机复验：
  导航生效且 0 未捕获异常。

## v0.11.1 紧急修复（宿主兼容 + 启动崩溃 · 2026-11-08）

**事故背景**：桌面端 DSH 自动升级到 `dsh 0.2.2-rc.1` 后连续崩溃（5 次/3 分钟），
守护插件被兼容闸门移出 profile、不再保护；重新挂载后又因遗留写锁把宿主拖进
`fatal load failure`。本版本修复三处，全部是「守护不能拖垮宿主」的底线问题。

- **宿主预发布版本兼容（P0）**：`engines.dsh` 与全部 `@deepseek-ai/dsh-*`
  peer 范围改为显式预发布分支
  `>=0.2.1-rc.5 <0.2.2-0 || >=0.2.2-rc.1 <0.2.3-0 || >=0.2.3-rc.1 <0.3.0-0`。
  原因：node-semver 只放行「与范围中某个比较符 **major.minor.patch 元组相同**
  且自身带预发布标签」的预发布版本 —— 旧范围 `>=0.2.1-rc.5 <0.3.0-0` 会
  静默排除 `0.2.2-rc.1`，插件被兼容闸门判为不兼容并从 profile 移除。
  已在 `dsh 0.2.2-rc.1` 干净沙箱（sb-rg-v0111）实测安装 + 启动 + 守护激活通过。
- **启动绝不抛出（P0）**：`boot()` 失败改为**降级留痕**（步骤记失败 + 警告
  日志），不再 rethrow。此前一个可恢复的写锁超时会把宿主变成
  `dsh: fatal load failure`（退出码 1）—— 观测/恢复设施不能拖垮主流程。
- **失效写锁自愈（P0）**：新增 `cleanStaleLocks`（Store.init 启动时清理 +
  `updateState` 超时后清理重试一次）。判据：锁内容为空/非正整数 PID（不完整
  记录，atomic-write 永远无法接管）/ PID 对应进程已死，且文件年龄 > 5s
  （避开锁创建与写 PID 之间的零字节窗口，绝不抢活锁）。
  真机事故：崩溃恰好发生在锁创建与写 PID 之间，遗留 0 字节
  `state.json.lock`，此后每次启动都等满超时并致命。
- **连续崩溃兜底升级（P0）**：`assessConfidence` 新增安全网 —— 累计崩溃
  `crashSeq ≥ 3` 时即使概率计数未达 `confirmRounds` 也强制行动；同时
  `readCrashHistory` 跳过启动时的「无嫌疑 crash-detected」记录。实测该记录
  每轮打断连续计数，导致 crashSeq 涨到 3 仍停在「观察中 1/2 轮」，崩溃循环
  永远无法自愈。
- 测试：新增 `tests/unit/store-lock.test.ts`（锁自愈 11 断言）与契约层
  预发布范围守卫；14/14 全绿（Core 7 / Host 2 / Client 4 / Contract 1）。

## 它解决什么问题

在 DSH 里添加或更新一个第三方 / 实验性插件后，DSH 可能直接崩溃退出：

```
dsh: fatal uncaught exception: Error: ...
```

崩溃发生在插件启动阶段，所以此时**插件本身已经无法运行**，也就无法自己写任何恢复逻辑。传统做法是：手动禁用所有插件 → 重启 → 逐个加回 → 每次重启验证。这既慢又容易再次踩坑。

本插件把这件事自动化：

| 步骤 | 传统做法 | 本插件 |
| --- | --- | --- |
| 记录安装/更新日期 | 靠记忆 | 自动写入日志（崩溃也不丢） |
| 备份插件配置 | 靠手动复制 | 自动备份到 `.recency-guard/backups/` |
| 崩溃后定位嫌疑 | 靠猜 | 按"最近更新"排序 |
| 禁用插件 | 手动改配置 | 自动写入决策文件，重启即生效 |
| 反复崩溃 | 重复手工操作 | 第 2 次崩溃自动多关一个 |
| 恢复配置 | 手动逐个加回 | 非首要嫌疑自动恢复 |

## 工作原理

### 1. 崩溃是怎么发生的

DSH 的 Loader 会捕获插件 `apply` 中抛出的错误，让该插件失效但不影响其它部分。真正致命的是**未被捕获的 rejection / 未捕获的异常**：Harness 的 fail-loud 处理器会把它们变成一次 `exit(1)`，整个 DSH 随之退出。

这意味着恢复**必须发生在崩溃插件被加载之前**，而不是之后。

### 2. 崩溃检测：进程级哨兵

Harness 在**正常退出和崩溃时都会**释放插件的 fiber，所以插件的 `dispose` 回调无法区分二者。能区分的是**退出码**：正常退出是 0，崩溃是 1。

因此本插件在**进程级**注册 `process.on('exit')`（不是 fiber 级 —— cordis 的 disposer 逆序执行，fiber 级的监听器会在进程真正退出前被移除）：

- 退出码非 0 → 写入 `.recency-guard/crashed` 哨兵文件
- 同时**同步**写出 `.recency-guard/decision.json` 恢复决策

### 3. 恢复决策：在插件被加载之前生效

Loader 支持给 patch 行写一个 `disabled: !!js "<表达式>"`。关键在于：**Loader 在导入该行的模块之前就会求值这个表达式**。

本插件为每个第三方插件在 profile 的 `cordis.patch.yml` 中写入这样一行（安装时自动完成）：

```yaml
- id: some-third-party-plugin
  name: dsh-some-third-party-plugin
  disabled: !!js "(() => { try { const fs = process.getBuiltinModule('fs'); const profile = ctx.get('profileContext'); if (!profile || !profile.dir) return false; const file = profile.dir + '/.recency-guard/decision.json'; if (!fs.existsSync(file)) return false; const decision = JSON.parse(fs.readFileSync(file, 'utf8')); return Array.isArray(decision.disable) && decision.disable.includes('dsh-some-third-party-plugin'); } catch { return false } })()"
```

表达式读取上一轮崩溃时写下的决策文件，命中就把该插件挡在门外 —— **崩溃插件的代码根本不会被加载**，崩溃自然不会重演。

> 表达式运行在 Loader 的 `with (ctx) { eval(expr) }` 作用域里：有 `ctx` 和 `process`，没有 `require`。`process.getBuiltinModule('fs')` 在该作用域可用，因此表达式能同步读到决策文件。

### 4. 为什么要"崩溃时"而不是"下次启动时"写决策

Loader 并发创建各个行。如果等到下次启动、守护插件自己加载时才写决策，决策可能**晚于**嫌疑插件那一行的求值，竞态会让嫌疑插件照常加载。

所以决策在**崩溃退出的那一刻**就写好：那时决策文件已经在磁盘上，下一次启动的第一个被求值的就是它。

### 5. 嫌疑排序

嫌疑 = profile 里声明的、**非官方**（`@deepseek-ai/*` 除外）、且**不是本插件自己**的依赖。排序依据：

1. 日志中的安装/更新事件（权威）
2. `node_modules` 的 mtime（首次运行时兜底）

排除官方包是为了保证恢复机制永远不会误伤 harness 自身；排除本插件自己，是因为关掉它就等于关掉恢复机制。

## 配置

在 profile 的 `cordis.patch.yml` 中：

```yaml
- id: recency-guard
  name: dsh-recency-guard
  config:
    enabled: true              # 总开关；false 时只记录，绝不自动关闭
    includeExperimental: true  # 是否把 experimental/beta 命名的包算作嫌疑
    maxAutoDisable: 2          # 单次恢复最多关闭几个嫌疑插件
    autoRestore: true          # 稳定后自动恢复非首要嫌疑的配置
    confirmRounds: 2           # 概率性证据的行动阈值（唯一嫌疑不受限）
    versionedBackups: true     # 插件更新时写带版本的时间线备份
    backupRetain: 5            # 每插件保留几份时间线备份
    backupRoot: ''             # 备份自定义目录（留空=profile 内分区目录）
```

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关。关闭后插件只记录日志，永不自动禁用任何插件 |
| `includeExperimental` | `true` | 实验性/beta 命名的包是否算嫌疑 |
| `maxAutoDisable` | `2` | 单次恢复最多关闭几个。崩溃次数递增，但封顶于此值 |
| `autoRestore` | `true` | 稳定启动后自动重新启用非首要嫌疑 |
| `confirmRounds` | `2` | 多嫌疑时同一头号嫌疑连续 N 轮崩溃才自动关闭（唯一嫌疑第 1 轮即行动） |
| `versionedBackups` | `true` | 插件更新时写「带版本的时间线备份」，可逐版对账 |
| `backupRetain` | `5` | 每个插件保留的备份份数（超出删最旧） |
| `backupRoot` | `''` | 备份自定义目录；环境变量 `RECENCY_GUARD_BACKUP_ROOT` 优先 |

## 数据文件

全部位于 profile 目录下：

```
<profile>/.recency-guard/
├── current.json          # 指针文件：当前分区键（守护行的 disabled 表达式经它搭桥）
├── partitions.json       # 分区索引：项目 → 分区键（多项目隔离的登记处）
├── projects/<分区键>/    # 每个项目的分区目录（状态/日志/决策完全独立）
│   ├── journal.jsonl     # 只追加的事件日志：install / update / crash-detected / disable / restore …
│   ├── snapshot.json     # 上次观测到的 { 插件名: 版本 }，用于识别更新
│   ├── state.json        # 崩溃计数、被自动关闭的插件、已恢复的插件
│   ├── decision.json     # 本轮要拦截的插件（守护行的表达式读它）
│   ├── crashed           # 崩溃哨兵：非零退出码时写下
│   ├── observation-*.json # 观测快照（启动事实，量化指标的数据源）
│   ├── archive/          # 本分区的历史归档（搬走+留档）
│   └── backups/          # 关闭前备份的配置（versionedBackups 时带版本）
└── …
```

## 恢复流程

```
第 1 次崩溃
   └─ 退出码非 0 → 写哨兵 + 决策（关闭最近更新的 1 个嫌疑）
第 2 次启动
   └─ 决策文件已就位 → 嫌疑插件的模块不被加载
      ├─ 仍然崩溃 → 关闭数 +1（最近更新的 2 个）
      └─ 启动成功 → 视为恢复
第 3 次启动（稳定）
   └─ 自动重新启用除首要嫌疑外的插件
      └─ 首要嫌疑保持关闭，等你确认后用 reenable 手动开启
```

**首要嫌疑**（最后被关闭的那个）会一直保持关闭，直到你明确用 `reenable` 开启它 —— 避免刚恢复就再次崩溃。

## 安全边界

本插件在设计上刻意保守：

- **只碰第三方插件**：`@deepseek-ai/*` 官方包永远不是嫌疑，harness 核心不会被关掉。
- **不碰自己**：`dsh-recency-guard` 永远不在嫌疑名单里。
- **决策文件缺失 / 损坏时一律放行**：表达式在任何异常下都返回 `false`，插件照常加载。守护机制**永远不会**把 profile 锁死在插件之外。
- **无法读取时不影响启动**：所有文件操作都包在 `try/catch` 中，失败只记录日志。
- **官方包与 harness 组件不受影响**：崩溃检测只影响"用户自己加的插件"这一层。
