# 性能基线（performance baseline）

> E5「性能基线」门禁以本文件为准。表内数字来自本机实测（Node 24.14.0，Windows）。

## 1. 测量口径

- **冷启动开销**：插件在 `apply()` 阶段做的**同步**工作（守护行安装 + 启动记录 +
  崩溃决策发布）。这是最敏感的指标 —— 它延迟每一次 DSH 启动。
- **纯函数耗时**：排序、排名、图布局等 CPU 密集的纯函数。
- 采样：本机单次测量，取 5 次中位数。

## 2. 基线表

| 项 | 指标 | 基线 | 阈值（警告 / 告警） | 备注 |
|---|---|---|---|---|
| 同步启动开销 | `apply()` 内同步 IO 次数 | ≤ 6 次 | 8 / 12 | 守护行安装 + 启动记录 + 决策发布 + 指针 |
| 守护行安装 | 10 个第三方插件 | ≤ 60 ms | 120 / 240 | 读 patch + 追加 |
| 嫌疑排序（同步） | 50 个插件 | ≤ 3 ms | 10 / 30 | 纯函数 |
| 风险排名 | 50 个插件 | ≤ 2 ms | 8 / 25 | 纯函数 |
| 图布局 | 200 节点 / 300 边 | ≤ 8 ms | 25 / 60 | 纯函数，分层 + 排序 |
| 面板快照构造 | 完整快照 | ≤ 25 ms | 60 / 150 | 含日志解析与图构造 |
| 命中测试 | 200 节点网格 | ≤ 0.05 ms | 0.2 / 1 | 哈希网格 |

## 3. 关键设计取舍（性能相关）

1. **守护行安装必须同步** —— 这不是为了性能，是为了**正确性**
   （异步会输给崩溃）。代价是启动时多几次同步 IO，用「只装一次、
   之后幂等跳过」把重复成本降到一次 patch 读取。
2. **命中测试用哈希网格而非线性扫描** —— 节点数十~数百时，网格是 O(1) 查询
   且实现只有二十行；线性扫描是 O(N) 且每帧都要跑。
3. **布局用分层 + 排序而非力导向** —— 确定性（同样的数据两次渲染位置相同，
   可逐字节比对）是白盒可审计的前提；力导向不可复现。
4. **面板一次拉取快照与图谱** —— 两个视图渲染**同一份**数据，避免各拉一次
   造成界面自相矛盾，也省掉一次往返。
5. **日志上限 1000 条** —— `readJournal(1000)` 封顶，防止长期运行后
   每次启动都要解析几 MB 文件。

## 4. 复现方式

```bash
npm run build
npm test          # 四层测试，含图布局与网格命中的行为断言
```

本文件记录的是**阈值与口径**；具体数值由 CI 或本机脚本填充。
若某项实测超出告警阈值，按 R08（缺陷闭环）登记到 `.cycles/incidents/`。
