### 3.1 故障注入是怎么做的（没有引入 IO 注入框架）

全部用**真实文件系统形态**制造失败，不 monkey-patch：
- rename 落点是已存在目录 ⇒ EPERM；临时路径预置成非空目录 ⇒ 写 EISDIR、清理 ERR_FS_EISDIR；
- 目录名先占成**普通文件** ⇒ ENOTDIR（分区索引/备份目录）；
- 缺失产物 ⇒ ENOENT（归档读 state/journal）；
- 死 pid ⇒ ESRCH；pid 0 ⇒ `process.kill(0,0)` **成功**（这是平台事实，见 §4.3）；
- rename 目标是非空目录 ⇒ 失败（哨兵清理）。

### 4.3 撤销的错误等价：`data/store.ts pid <= 0`（本轮自查发现）

cycle-13 把它登记为等价，理由引用的是 **sentinel 的 `pidAlive(0) === false`**。但 store 侧用的是**另一份实现**
`processAlive`；本轮实测：

```text
process.kill(0, 0)  ⇒  成功（pid 0 = 当前进程组）
process.kill(-1, 0) ⇒  ESRCH
```

即 `processAlive(0) === true`。于是 `pid <= 0 → < 0` 在 pid=0 时：
原版判「不完整记录」⇒ 删除锁；变异版判「活进程持有」⇒ **保留锁** ⇒ atomic-write 等满超时 = fatal load failure
（v0.11.1 那条紧急修复保护的正是这个）。**行为不同，不是等价。**

处置：从账本撤除该条 → 补断言「内容为 "0" 的锁必须被清理」→ 最终轮 **KILL**。
教训：**等价理由依赖的断言必须来自同一实现**；换了模块/实现，等价性不跟随。

  真红文件每次都会红 ⇒ FATAL。尝试次数写入控制台与报告（不隐藏）。
- **自证**：本轮工具两次拦下真红基线 —— ① `tests/client/insight-cards.test.ts` 因 `locale/en.json` 非法 JSON
  直接崩（他域中间态）；② `fault-injection` 当时因两个真实竞态而红（我最初误判为「抖动」，见 §0.1 ——
  工具拦下的是**真红**，只是我给的原因标签错了）。假绿轮的 43/44 在新工具下无法复现。

## 7. 残留风险（诚实边界）

1. **95.3% 不是「测试强度 95.3%」**：分母只是四种文本变换（comparison / try-catch / phase / pointer-path）
   能生成的变异体；本项目的主流缺陷（结构/时序/并发）不在分母里。该数字证明的是「这些写坏方式会被断言抓住」。
2. **我曾把两个真实竞态误判成「环境抖动」**（§0.1）：`fault-injection` 单跑能过，我就下了「偶发、非缺陷」的结论；
   evidence 用失败保留现场 + `FI_ONLY` 连跑 30 轮证明是 journal 整写覆盖与 crashSeq 覆盖两个**确定性竞态**。
   修复后 `FI_ONLY=required` 8/8、完整故障注入 5/5。教训：**不可复现 ≠ 不存在**；判「抖动」必须有现场证据。
3. **等价判定会随重构漂移**：本轮发生 6 次行号漂移 + 1 次语义被推翻（§4.3）。账本不是一次性资产，每轮必须重生成校验。
4. **剩余 2 条未归因都已定性、不是「没归因」**：markov:166 是不可达代码（工具边界），
   store:297 是已登记 TD-5 的 IO 边界（模块级静态 `readFile` 不可 mock，或需把纯数据层改成可配置 IO 层）。
   按纪律留在分母，未混进等价账本。
5. **语法杀死 0** 说明四类变异子的文本变换已经收窄（`\s*` 跨行、标识符切半的问题在 cycle-13 已修）。
6. 本报告**不能**替代真机用户旅程；它证明「代码被这样改坏时断言会响」，不证明产品在真机上是对的。
7. 全量变异只跑了一遍（53 个变异体），没有做重复性研究；重型沙箱测试仍有偶发失败可能，
   但 G 轮的基线自检（35 文件全绿、1 次通过）+ 故障注入稳定性实测（8/8、2/2）降低了这个风险。
8. **冻结纪律**：G 轮是 `src/**`+`tests/**` 冻结后的唯一一次门禁；若后续仍要动代码，必须重跑并重锚，
   不能沿用 95.3%。
