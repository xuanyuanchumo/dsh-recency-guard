## 4. 修复点（`src/host/surface/tool-text.ts`）

### 4.1 缺陷 1：组合字符/零宽字符被算成 1 列

`displayWidth` 旧实现只有两档：宽字符 2、其余 1。于是：
- `e` + `U+0301` → 2 列（真实 1 列）⇒ 含重音的名字把右侧列推右一格；
- `a` + `U+200B` + `b` → 3 列（真实 2 列）⇒ 段尾多出不可见的一格；
- `👍🏽`（emoji + 肤色修饰符）→ 4 列（真实 2 列）。

修法：新增 `isZeroWidth(cp)`，覆盖组合用附加符号（`0300–036F` 等 6 段）、变体选择符、
肤色修饰符、ZWSP/ZWNJ/ZWJ/LRM/RLM/word-joiner/BOM/软连字符；`codePointWidth` 先判零宽，
再进宽域判定（顺序很重要：肤色修饰符落在 emoji 宽域内，必须先判 0）。

### 4.2 缺陷 2：ZWJ 序列按分量累加

`👨‍👩‍👧` = 3 个 emoji + 2 个 ZWJ：旧实现 2+1+2+1+2 = 8（ZWJ 修复后 6），真实 1 个字形 2 列。
修法：`displayWidth` 跟踪 `joined`，ZWJ 之后的码点不再累加；`clipWidth`/`wrapWidth`
用同一口径，避免「预算在字形中间耗尽」把序列硬断。

### 4.3 为什么没有动 `bin/rescue.mjs`

`bin/` 不在本任务写域（写域：`scripts/mutation.mjs` / `tests/unit/*` / `src/host/surface/tool-text.ts` / `.cycles/**`）。
rescue 自带宽度的原因写在它自己的注释里（崩溃后 `node_modules` 可能损坏，逃生通道必须零依赖），
**这解释合理，但两份实现必然漂移**（CLAUDE.md 已登记过一次同类事故：`LAYOUT` 各写一份导致小地图整体偏移）。
登记为下轮项：把 `codePointWidth/isZeroWidth` 收敛到 `src/shared/text-width.ts`（无副作用纯函数，
host 与 bin 各引一份；bin 用相对路径 import 即可，仍零第三方依赖）。

## 5. 回归断言（`tests/unit/core.test.ts`，全部 PASS）

| 断言 | 钉住的事实 |
|---|---|
| `displayWidth('中文') === 4` | CJK 全宽 2 列 |
| `codePointWidth(0x0300) === 0` / `codePointWidth(0x036f) === 0` | 组合符号区间两端（含变异边界） |
| `displayWidth('e\u0301') === 1` | 组合字符不增宽 |
| `displayWidth('a\u200bb') === 2` | 零宽空格不占列 |
| `displayWidth('🎉') === 2` | emoji 代理对 |
| `displayWidth('👨‍👩‍👧') === 2` | ZWJ 序列是一个字形 |
| `displayWidth('👍🏽') === 2` | 肤色修饰符不增宽 |
| `displayWidth(padWidth('更新', 8)) === 8` | 右填充按显示列 |
| `wrapWidth('中'.repeat(10), 5)` 每行 ≤5 且拼回原文 | CJK 折行不超预算、不丢字符 |
| `wrapWidth('🎉'.repeat(10), 5)` 每行 ≤5 且拼回原文 | emoji 折行不拆代理对 |
| `clipWidth('abcde', 4) === 'abc…'` | 内容预算 = max−1（`…` 占 1 列） |

> 断言锚点取自实现原文的**区间边界与常量**（`0x0300/0x036f`、`max−1`、`MAX_LINE_WIDTH`），
> 不是凭印象猜的近义词 —— 这是 v0.14「`/省略/` 匹配 `其余 N 项未展开`」的教训。

## 6. 诚实边界

1. **本轮只验证了「命令窗口文本」这一条通道**。Web 卡片的 CSS 列宽、字体回退（emoji 字体缺失时
   渲染成方框）不在 Node 进程可测范围 —— 文本层的显示宽正确不等于浏览器里一定对齐。
2. **宽度表按 Unicode 区块近似**，不是完整的 UAX #11/Unicode 15 宽表。已知未覆盖：
   旗标序列（两个 regional indicator 各算 1 → 合计 2，恰好正确）、keycap `1️⃣`（算 1 列，真实 2 列）、
   泰文/阿拉伯文连写。这些都是「宁可少算不多算」的保守取舍，且不影响中文/emoji 主路径。
3. **`bin/rescue.mjs` 的第二份实现仍是旧口径**（见 §4.3），本轮 rescue 输出恰好只用到
   ASCII kind + 中文 subject（中文在列尾），因此实测未错位；一旦 `kind` 或时间列出现 emoji，
   rescue 会错位。这是明确的残留风险，不是"看起来没问题"。

## 7. 逃生通道双形态：只读 vs `--yes`（**交付清单可直接引用**）

> **可直接引用的结论（一段话）**
>
> `bin/rescue.mjs` 是宿主起不来时的离线逃生通道，采用**双形态**：`status / history / decision / archives / rescues`
> 五个只读命令**绝不写盘**（整棵 profile 树的内容指纹前后逐字节一致）；`apply / restore` 两个可写命令**默认也是只读**——
> 不带 `--yes` 只打印「将会发生什么」的 dry-run 计划，只有显式 `--yes` 才落盘。写路径是**两阶段提交**：先把
> `prepared` 记录（含 `beforeHash/afterHash` 与每个被摘除 bundle 的原 index）原子落盘，再原子改 profile，最后标
> `applied`；`restore` 按原 index 精确回插并标 `restored`，**逐字节可逆**。在沙箱 profile 上的 22 条行为断言全部通过
> （`ALL PASS`），证据日志见 `.cycles/verify/r10-rescue-dual.log`。

### 7.3 纪律边界（引用时请一起引用）

1. 这条结论证明的是**文件系统行为**（只读不写、dry-run 不写、`--yes` 两阶段可逆），
   **不证明**「逃生操作在真机上一定能把宿主救回来」—— 那要跑真机用户旅程。
2. 两阶段记录的 `restore --resume` 中断恢复只验证了「正常 applied→restored 路径」与「记录含原 index」；
   **没有**在真机上做「apply 与 restore 之间被强杀」的注入（那属于故障注入里程碑）。
3. dry-run 的输出是给人看的计划；真机误用 `--yes` 的风险由「必须显式传 flag」这一层挡住，
   没有交互式二次确认（CLI 逃生通道的取舍：崩溃现场没有可交互的终端）。
