# 06 · 应用场景与泛化

> 目的：`dsh-recency-guard` 的价值不只是「DSH 插件守护」。本篇把它抽象成一个
> **可移植的故障应对模式**，并给出每个领域的适配清单。
>
> 原则：**先抽象，再套用**。抽象错一次，所有移植都会错。

## 0. 从本项目提炼的通用模式

本项目做的事，本质是：

> **当系统因「最近的人为变更」而崩溃时，用「变更的新鲜度」作为第一嫌疑人，
> 用「概率性证据 + 确认轮数」控制误伤，用「两阶段提交 + 备份」保证可逆，
> 用「诚实边界 + 可观测」保证不撒谎。**

把它写成五元组：

| 要素 | 本项目实现 | 泛化后的问法 |
|---|---|---|
| **信号** | 崩溃（哨兵 + 残留标记双通道） | 系统出了什么「非预期终态」？ |
| **嫌疑键** | 最近安装/更新的插件 | 什么是「最近人为变更」？ |
| **动作** | 关闭嫌疑插件 | 最小可逆的「隔离动作」是什么？ |
| **证据阈值** | 确定性 1 轮 / 概率性 `confirmRounds` | 多少证据才动手？ |
| **诚实边界** | `Metric<T>` 的 `defined/null` | 什么情况下「不能判定」？ |

### 0.1 三个不可移植就失效的前提

1. **变更是可观测的**（有安装/更新事实或时间戳）；
2. **隔离是可逆的**（能关闭、能放回、能回滚）；
3. **信号是明确的**（能区分「崩溃」与「正常退出/并发/重载」）。

三个前提不满足，这个模式就不适用——见第 4 节「不适合的场景」。

## 1. 场景总览

| # | 场景 | 信号 | 嫌疑键 | 隔离动作 | 诚实边界 |
|---|---|---|---|---|---|
| 1 | IDE / 编辑器插件 | 进程崩溃 / 插件宿主无响应 | 最近安装/更新的插件 | 禁用插件、回退版本 | 无崩溃记录 ≠ 稳定 |
| 2 | 浏览器扩展 | 扩展页崩溃 / 宿主标签页白屏 | 最近更新的扩展 | 停用扩展 | 扩展 API 限制，可能无法完全隔离 |
| 3 | CI/CD 流水线 | 构建失败 / 作业 OOM | 最近变更的依赖 / commit | 回退 commit、钉住依赖版本 | 构建失败原因多样，易误判 |
| 4 | Kubernetes Operator | Pod CrashLoopBackOff | 最近变更的 Helm values / 镜像版本 | 回滚 rollout、禁用 webhook | 集群状态复杂，需限流 |
| 5 | 模型训练 | 训练进程 OOM / NaN | 最近变更的超参 / 数据版本 | 回退 checkpoint、钉住数据版本 | NaN 可能来自数据而非代码 |
| 6 | 微服务依赖 | 服务启动失败 / 健康检查失败 | 最近发布的版本 | 摘除实例、回滚发布 | 启动失败可能是资源不足 |
| 7 | npm / pip 依赖守护 | 安装后构建失败 | 最近变更的依赖 | 锁定版本、移除依赖 | 传递依赖难以定位 |
| 8 | 设计工具 / 桌面软件 | 应用崩溃 | 最近安装的插件/字体/驱动 | 禁用插件、回退配置 | 崩溃可能来自系统层 |
| 9 | 自动驾驶 / 机器人 | 控制异常 / 传感器失效 | 最近变更的模型/固件/配置 | 切入安全模式、降级 | 安全相关，必须人审 |
| 10 | 医疗设备 / 生命支持 | 设备告警 | 最近变更的配置/固件 | 报警 + 停止自动变更 | 极高风险，禁止自动行动 |

## 2. 逐场景适配说明

### 2.1 IDE / 编辑器插件（最接近本项目）

- **信号**：`crash` 事件 / 进程非零退出 / 插件宿主「无响应」。
- **嫌疑键**：`node_modules` 的 mtime + 插件管理器的安装日志（本项目已做）。
- **隔离动作**：在插件被加载前禁用（`disabled` 声明），等价于本项目的守护行。
- **证据阈值**：与本项目一致——确定性证据（唯一嫌疑）立即动手；概率性证据 `confirmRounds` 轮。
- **诚实边界**：无崩溃记录 ≠ 稳定；「插件被禁用」≠「插件被修复」。
- **本项目可复用**：`recency.ts`、`recovery-policy.ts`、`decision.ts` 的**全部**逻辑。

### 2.2 浏览器扩展

- **差异**：扩展 API 限制，可能无法「在加载前拦截」；只能用「停用」而非「禁用加载」。
- **诚实边界**：扩展被停用后，宿主行为可能不立即恢复（缓存、存储残留）。
- **建议**：动作阈值应更保守（`confirmRounds` 更大），因为「停用」对用户体验影响更大。

### 2.3 CI/CD 流水线

- **差异**：信号是「构建失败」而非「进程崩溃」；嫌疑键是「最近变更的 commit / 依赖」。
- **隔离动作**：回退 commit、钉住依赖版本。
- **诚实边界**：构建失败原因多样（网络、缓存、磁盘、编译器版本），「最近变更」不一定是根因。
- **建议**：引入**分层归因**（本项目 `recency.ts:65` 的官方/实验/第三方分层可直接移植）；
  构建系统通常有结构化日志，可用作「确定性证据」的来源。

### 2.4 Kubernetes Operator

- **差异**：信号是 `CrashLoopBackOff` / 探针失败；隔离动作是 `rollout undo` / 摘除实例。
- **嫌疑键**：最近变更的 Helm values / 镜像 tag / CRD 版本。
- **诚实边界**：集群状态复杂，自动回滚可能掩盖根因；必须限流 + 人审。
- **建议**：移植「两阶段提交」（先 `prepared` 记录再执行）与「重启对账」（按集群现状 reconcile）。

### 2.5 模型训练

- **差异**：信号是 OOM / NaN / loss 发散；嫌疑键是最近变更的超参 / 数据版本。
- **隔离动作**：回退 checkpoint、钉住数据版本。
- **诚实边界**：NaN 可能来自数据（脏样本）而非代码；「最近变更」可能是数据版本。
- **建议**：用本项目的 `intervalSurvival` 分析「训练崩溃间隔」的危险率方向——
  k<1 说明崩溃**成簇**（一次数据问题引发连锁），k≈1 说明是随机 OOM。

### 2.6 npm / pip 依赖守护

- **差异**：信号是「安装后构建失败」；嫌疑键是最近变更的依赖。
- **隔离动作**：锁定版本、移除依赖。
- **诚实边界**：传递依赖（transitive dependency）难以定位——一个直接依赖可能拉入
  多个间接依赖。
- **建议**：移植「嫌疑排名 + 确认轮数」，并扩展「依赖图」分析（本项目能力图
  `capability.ts` 的双向可达性可作起点）。

### 2.7 自动驾驶 / 机器人

- **差异**：安全相关，**必须人审**，禁止全自动隔离。
- **隔离动作**：切入安全模式 / 降级（而非完全停止）。
- **诚实边界**：自动行动的法律与伦理风险 > 技术风险。
- **建议**：移植本项目的 **HITL 门禁 H1–H4** 与「审计信封」（`change-guard.ts:105 ActionAudit`）——
  每次写动作留 `{actor, action, justification}`，供事后审计。

### 2.8 医疗设备 / 生命支持

- **不建议自动行动**。本项目的模式可用于**监测与告警**（诚实边界 + 可观测），
  但隔离动作必须由人执行。

## 3. 移植四步法

把本项目模式移植到新领域的标准流程：

### 第 1 步：确认三个前提

| 前提 | 检查 |
|---|---|
| 变更可观测 | 能否拿到「最近变更了什么」的事实或时间戳？ |
| 隔离可逆 | 能否关闭/回退/摘除，且能放回/恢复/重挂？ |
| 信号明确 | 能否区分「崩溃」与「正常退出/并发/重载」？ |

任一不满足 → 改用「监测 + 告警」而非「自动行动」。

### 第 2 步：定义五元组

填写第 0 节的表格。**关键**：证据阈值要保守起步（`confirmRounds` 取 2~3），
再按误伤率数据调。

### 第 3 步：实现可逆三件套

| 组件 | 作用 | 本项目落点 |
|---|---|---|
| 变更前备份 | 可回退 | `patch.ts` 时间线备份 |
| 两阶段提交 | 不留半成品 | `recovery-policy.ts:133 DecisionPhase`（reconcile 在 :260 `reconcilePrepared`） |
| 重启对账 | 崩溃后按磁盘现状 reconcile | `recovery-policy.ts` reconcile |

### 第 4 步：加验证

- 诚实边界测试（`defined:false` 断言）；
- 变异自证（写回缺陷 → 断言 FAIL）；
- 真机/真实环境用户旅程验证。

## 4. 不适合的场景（反例）

| 场景 | 为什么不适合 |
|---|---|
| 无变更的静态系统 | 没有「最近变更」可作嫌疑键 |
| 变更不可观测 | 无法排名 |
| 隔离不可逆 | 一旦动作就无法恢复，风险不可接受 |
| 崩溃原因完全随机（无相关性） | 「最近变更」不是有效信号，模式退化为随机猜测 |
| 高安全等级系统（医疗、航空） | 自动行动的法律/伦理风险 > 收益，必须人审或仅告警 |

**纪律**：**先确认前提，再谈移植。** 把「最近变更优先」当成万能药，是这类模式最大的风险。

---

## 5. 模式的边界与诚实说明

1. **这个模式不保证找到根因**。它只保证「让系统先活下来，并留下证据」。
   根因分析需要额外的可观测性（日志、trace、A/B 对照）。
2. **这个模式会误伤**。`confirmRounds` 只能降低误伤率，不能消除。
   误伤的代价是「用户少一个功能」，这是刻意选择的（优于「系统崩溃」）。
3. **这个模式依赖时间局部性假设**。如果「最近变更」与「崩溃」无相关性
   （例如崩溃由长期累积的资源泄漏引起），模式会失效。
4. **这个模式需要可逆性**。不可逆的隔离动作，必须在人审下执行。

## 6. 从本项目带走的最小资产

如果只想带走三样东西：

1. **`Metric<T>` 诚实边界**——无数据 ≠ 零；每个读数带 `formula/inputs/confidence`。
2. **`classifyAbnormalExit` 的四分支**——区分 `clean / self-reload / concurrent / abnormal`，
   防假归因。
3. **`computeRevision` 的事实哈希**——乐观并发，幂等，抗崩溃。

这三样，是本项目**跨语言、跨领域**都能复用的资产。
