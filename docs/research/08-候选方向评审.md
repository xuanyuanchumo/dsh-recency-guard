# 08 · 候选方向评审

> 目的：对四个候选优化方向做**基于代码事实**的评审。
> 评审方法：先核对每个方向的「实际缺口」描述是否与源码一致，再评判其数学/工程方案，
> 最后给出更优做法与优先级。
>
> 结论先行：**方向一、二、四的前提部分成立但方案次优；方向三前提有误但缺口真实、方案最优；
> 四个方向共同绕开了一个更大的缺口——决策路径与展示口径的排序分裂。**

## 1. 方向一：LRU-K 环形缓冲区 —— **前提成立，方案次优**

### 1.1 前提核对

> 原文：「当前嫌疑排序仅区分官方/非官方，同属非官方的插件之间，排序依据是最近一次时间戳」

**成立（F1）。** `rankByRecency` 确实只按 `lastChangeAt` 降序 + 同刻按名字兜底，
`riskScore` 的三因子（recency/experimental/crashFrequency）没有进入决策。

### 1.2 方案评判

| 问题 | 说明 |
|---|---|
| **语义错配** | LRU-K 的经典语义是「缓存淘汰：判断某页**最近是否被频繁访问**」。本场景要的是「插件**最近是否被频繁变更**」。LRU-K 的 K-distance 衡量「第 K 近一次**使用**」，不是「第 K 近一次**变更**」。要的是变更频率，不是访问频率——直接套 LRU-K 是把「访问」和「变更」混为一谈。 |
| **K-distance 对单事件插件无定义** | 原文说「K=2 时，一个仅触发过一次安装的插件，其 K-distance 可能很大（历史证据不足）」。但严格说，只有一个事件时第 2 近事件**不存在**，K-distance 无定义。项目纪律要求这种边界返回 `defined:false` 或显式退化，原文没给退化策略。 |
| **忽略了已有的信息通道** | 「热更新五次」若每次更新都崩，`streak`（F5）已经会很高——崩溃复现本身已建模。「更新频繁但稳定」的插件，其时间戳反而会让它排前面，但 streak 低说明它没引发崩溃。LRU-K 想区分的两类，streak 已部分区分。 |
| **绕过了真正的问题** | 为什么面板显示 `riskScore`（三因子）而决策用纯 `rankByRecency`？这是**排序口径分裂**——见第 5 节。方向一在分裂的下游再加一层排序，治标不治本。 |

### 1.3 更优做法

1. **先统一口径**：让决策路径使用 `riskScore` 排序，而不是 `rankByRecency`。
   这是优先级最高的修复（见第 5 节）。
2. **再增加频率因子**：在 `riskScore` 的三因子基础上加第四因子「变更频率」，
   用历史 `diffVersions` 事件计数 + 半衰期加权（与现有 recency 因子同构）。
   不必新建 LRU-K 层。
3. **单事件退化**：频率因子样本不足时按 `Metric.defined` 语义降级（不参与加权，
   只保留 recency 因子），与项目「无数据不当零」纪律一致。

### 1.4 工程约束核对

原文称「环形缓冲区更新 O(1)，堆操作 O(log n)，不影响现有毫秒级评分计算」——
复杂度描述基本成立，但标准 LRU-K 是「哈希表 + 双向链表 + 堆」三件套，
不是「定长环形缓冲区 + 堆」二件套。功能等价，但「定长环形缓冲区」只是
「保留最近 K 个时间戳」的实现细节，不是 LRU-K 的核心。

### 1.5 结论

**部分成立，优先级中。** 缺口真实，但「LRU-K」这个载体选错了语义；
应改为「变更频率因子 + 决策/展示排序口径统一」。

## 2. 方向二：证据年龄衰减 —— **前提成立，方案有副作用**

### 2.1 前提核对

> 原文：「confirmRounds 是纯轮次计数——只要同一嫌疑连续 N 轮复现就行动，不管这 N 轮之间隔了多久」

**成立（F5）。** `assessConfidence` 的 streak 只看 `entry.suspects[0]` 是否等于
当前 head，不看时间间隔。

### 2.2 方案评判

| 问题 | 说明 |
|---|---|
| **与已有指标重复** | 项目已有 `crashPressure`（EWMA of 0/1 启动信号，H=5，F9）和 `intervalSurvival`（Weibull，F10）。方向二本质是把 EWMA 从「启动级」下沉到「崩溃级」，属于复用已有思想而非新模型。应该先问：能不能直接用 `intervalSurvival` 的输出做证据权重？ |
| **可能增加漏判（放过真缺陷）** | streak 的语义是「同一头号嫌疑连续复现」。若环境未变（`environmentChanged` 已判），「间隔一天的两次崩溃」**仍然是该插件的确定性缺陷**，只是用户用得少。加时间衰减后，这种会被当成证据不足 → **放过真缺陷**，与项目既定原则「宿主可用性优先于误伤最小化」（`recovery-policy.ts:176-179`）冲突。 |
| **阈值无依据** | λ 取 12–24 小时，而 recency 半衰期是 72 小时（F2/`lifecycle.ts:370`）。两套半衰期无统一调参依据；θ 的标定也没有来源。项目纪律要求「每个参数都要有来历」。 |
| **作用面有限** | 原文说「保留 crashSeq ≥ 3 安全网」。但这意味着衰减证据只在 `streak < 3` 时起作用，而 `streak < 3` 恰恰是证据最弱、最不该行动的时候。真正强证据（streak ≥ 3）被安全网直接覆盖。 |

### 2.3 更优做法

1. **区分「偶然」与「持续」而非「新近」**：用已有 `intervalSurvival` 的
   `hazardDirection`——`k < 0.9`（成簇）说明崩溃有连带关系，应**更积极**行动；
   `k ≈ 1`（泊松）说明是独立随机事件，应**更保守**。这与方向二的直觉一致，
   但方向是「按分布形态调整」，不是「按时间间隔衰减」。
2. **衰减只用于概率性证据的辅助判据，不否决确定性复现**：
   明确纪律——「间隔长但环境未变的同嫌疑复现，仍按 streak 处理；
   衰减仅用于区分『刚崩一次』与『持续在崩』」。
3. **统一半衰期**：若要引入时间衰减，与 `RECENCY_HALF_LIFE_HOURS`（72h）
   对齐或显式论证为何不同。

### 2.4 结论

**部分成立，优先级低。** 直觉对（时间维度有信息），但实现方向（指数衰减）
与已有生存模型重复，且可能增加漏判。建议改用 `intervalSurvival` 的分布形态。

## 3. 方向三：决策因子贡献快照 —— **前提有误，缺口真实，方案最优**

### 3.1 前提核对

> 原文：「decision.json 当前只记录 disable 数组……决策的理由没有持久化」

**部分不成立（F3）。** `decision.json` 的 `suspects` 数组**已经**记录了每个嫌疑的
`{bundle, version, lastChangeAt}`（`index.ts:826-830`）。
所以「只记录 disable 数组」是错的。

**但缺口真实**：已记录的字段只有排序键（时间戳），**没有因子贡献**——
即 `riskScore` 的三因子分解、`streak` 计数、`K-distance` 等都不在盘上。
事后无法回答「为什么是 A 而不是 B」「A 的 experimental 因子贡献了多少」。

### 3.2 方案评判

| 项 | 评价 |
|---|---|
| 工程可行性 | **完全可行**。扩展 `Decision.suspects` 条目即可，`guardExpression` 只读 `disable`（F4），不受影响 |
| 与白盒纪律一致 | **高度一致**。项目核心纪律是「每个读数带 formula/inputs」，因子快照是这一纪律在决策层的落地 |
| 对调参的决定性 | **成立**。没有因子快照，任何模型调参都是盲调——这正是原文的核心论点，且正确 |
| 实现成本 | **低**。一个纯数据字段，无新算法，无新依赖 |

### 3.3 更优做法（基于已有字段扩展）

不要新增顶层字段，而是**扩展现有 `suspects[]` 条目**：

```jsonc
// decision.json 的 suspects[] 当前（F3）
{ "bundle": "dsh-foo", "version": "1.2.0", "lastChangeAt": "2026-11-10T..." }

// 建议扩展
{
  "bundle": "dsh-foo",
  "version": "1.2.0",
  "lastChangeAt": "2026-11-10T...",
  "evidence": {
    "rank": 1,
    "riskScore": 0.72,
    "factors": { "recency": 0.5, "experimental": 0.3, "crashFrequency": 0.2 },
    "streak": 2,
    "source": "journal"        // journal | mtime（已有 RecencyEntry.source）
  }
}
```

这样既保留现有字段（向后兼容），又补齐因子贡献。

### 3.4 结论

**缺口真实，方案最优，优先级最高。** 这是四个方向里唯一一个「低风险、高收益、
与项目纪律一致」的。应作为其他三个方向的前置（先有因子快照，才能验证方向一/二/四的
模型是否有预测力）。

## 4. 方向四：官方实验插件共现加权 —— **数据基础不存在**

### 4.1 前提核对

> 原文：「官方实验插件……观测数据被浪费了」「若某非官方插件依赖的底层模块与某官方实验插件共享」

**部分成立。** 官方实验观测确实只记录不进入风险评分（F7）。
但「共享底层模块」「依赖关系」这一前提**不存在**——项目没有插件间依赖图（F8）。

### 4.2 方案评判

| 问题 | 说明 |
|---|---|
| **依赖数据缺失** | `official-observe.ts:28-32` 只记录 `{bundle, version, enabled}`。没有依赖关系、没有模块共享信息。要做「共现加权」，必须先有插件间依赖数据——这是一个新的、未规划的数据采集。 |
| **共现 ≠ 因果** | 官方实验插件崩溃时，非官方插件可能只是「在同一时刻活跃」。共现信号会**增加误伤**（把无辜插件加权）。项目纪律是「宁可漏拦，不可过拦截」——共现加权方向相反。 |
| **与官方不干预纪律的张力** | 原文说「不改变不关闭官方实验插件的纪律」，但把官方插件的崩溃归因信息注入非官方插件的风险评分，等于让官方插件的崩溃**间接**影响非官方插件的关闭决策。这是对「官方组件风险不可接受」纪律的间接突破，需要更谨慎的论证。 |
| **可证伪性差** | 没有因子快照（方向三）就无法验证「共现」是否真有预测力。先上模型再验证，违反项目「先验证假设再行动」的迭代纪律。 |

### 4.3 更优做法

1. **先做方向三**：采集因子快照，把「崩溃时官方实验插件是否活跃」作为一个可观测字段。
2. **用数据验证共现信号**：离线回放历史崩溃，统计「官方实验插件活跃时非官方插件的
   命中率」vs「不活跃时」。若差异显著，再考虑加权。
3. **若做，用一阶共现但保守加权**：权重不超过 0.1，且只在「官方实验插件在崩溃窗口内
   确实变更过」时触发（比「活跃」更严格）。
4. **明确不违反官方纪律**：写入注释——「官方实验插件的观测数据只用于**归因展示**与
   **非官方插件的辅助加权**，绝不用于决定关闭官方组件本身」。

### 4.4 结论

**缺口部分成立，数据基础不存在，优先级最低。** 应先做方向三，用数据验证。

## 5. 四个方向都绕开的最大缺口：决策与展示的排序分裂

这是本次评审最重要的发现。

### 5.1 事实

| 路径 | 用的排序 | 代码 |
|---|---|---|
| 决策关闭谁 | `rankByRecency`（纯时间戳） | `index.ts:797` → `recency.ts:121` |
| 面板展示风险 | `riskScore`（三因子） | `observability.ts:739` |
| 决策文件 suspects | 纯时间戳排序 | `index.ts:826-830` |

### 5.2 后果

**用户看到的「风险排名」与实际「被关闭的顺序」不是同一套逻辑。**
一个 `riskScore` 很高（experimental=1、crashFrequency 高）但最近没更新的插件，
面板显示高风险，却不会被列入关闭名单；而一个刚更新、`riskScore` 低的插件会被关闭。

这不是 bug，是**设计选择**（崩溃时决策要快、要可解释、要确定性），但它造成了：

1. 用户困惑：「为什么高风险的没被关？」
2. 方向一/二/四的模型无法被验证——因为**决策路径根本不消费这些模型**。
3. 因子快照（方向三）的价值被削弱——因为快照的是排序键，不是决策用的完整依据。

### 5.3 建议

**短期**：在 `decision.json` 的 `suspects[]` 里同时记录 `riskScore` 与 `rank`，
让面板能解释「为什么按时间戳关闭这个，而它的风险分是 X」。

**中期**：让决策路径在「确定性证据」（唯一嫌疑）下仍用 `rankByRecency`（快、确定），
但在「概率性证据」下改用 `riskScore` 排序头号嫌疑。即：**确定性用时间戳，概率性用风险分**。

**长期**：统一排序口径，让 `rankByRecency` 退化为 `riskScore` 的 recency 因子输入。

### 5.4 结论

**优先级最高。** 这个缺口不解决，方向一/二/四的模型改进都无法在决策路径上生效。

## 6. 优先级与依赖关系

```
P0  方向三（因子快照）        ← 前置：没有它，其他方向无法验证
P0  第5节（排序口径统一）     ← 前置：决策路径不消费模型，模型改进无效
P1  方向一改造（变更频率因子，并入 riskScore）
P2  方向二改造（改用 intervalSurvival 分布形态，而非指数衰减）
P2  方向四（先采集共现数据，验证后再加权）
```

### 依赖链

```
方向三（快照）──▶ 验证方向一/二/四的模型是否有预测力
      │
      ├──▶ 方向一（频率因子，并入 riskScore，配合第5节统一口径）
      ├──▶ 方向二（用生存分布形态，配合第5节统一口径）
      └──▶ 方向四（用快照验证共现信号）
```

### 每个方向的落地前检查

| 方向 | 落地前必须回答 |
|---|---|
| 方向一 | 决策路径是否已统一到 riskScore？（否则加了频率因子也没人用） |
| 方向二 | 衰减是否会否决环境未变的确定性复现？（若会，违反可用性优先原则） |
| 方向三 | suspects 条目是否向后兼容？（老版本读 decision.json 不崩） |
| 方向四 | 共现信号在历史数据上的预测力是否显著？（否则不落地） |

## 7. 评审的元规则

1. **先核对前提，再评判方案**。四个方向里三个的前提与代码不符或部分不符——
   如果直接按原文实施，会解决一个不存在的问题。
2. **检查是否与已有模型重复**。项目已有 EWMA（crashPressure）、Weibull（intervalSurvival）、
   三因子风险评分——新方向要先问「能不能复用」。
3. **检查数据基础是否存在**。方向四的「依赖共享」在代码里不存在。
4. **检查是否违反项目既定原则**。方向二可能增加漏判、方向四可能增加误伤，
   都与「宿主可用性优先」「宁可漏拦不可过拦截」有张力。
5. **检查可证伪性**。没有因子快照，任何模型改进都无法验证。

这五条，是评判任何后续方向的固定流程。
