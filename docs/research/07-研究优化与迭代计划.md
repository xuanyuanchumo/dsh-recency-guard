# 07 · 研究优化与迭代计划

> 目的：把本套文档的洞察，变成**可执行、可度量、可证伪**的迭代计划。
> 每个计划项都有：假设、实验、度量、判据、落地位置、风险。
>
> 对齐项目治理：本计划与 `.cycles/config.yml` 的 `macro_cycle`（plan → design → build →
> test → deploy → maintain）、门禁 G0–G3、评估维度 E1–E8、控制带
> （`crash_rate` warning 0.02 / alarm 0.05，`stability_score` warning 0.6 / alarm 0.3）一致。

## 1. 研究方向地图（四个 RQ）

| RQ | 问题 | 产出 | 优先级 |
|---|---|---|---|
| RQ1 | **归因更准**：如何把「最近更新」从相关性升级为更可靠的因果证据？ | 贝叶斯 / 生存-因果融合模型 | P0 |

## 2. RQ1 · 归因更准：从相关性到因果证据

### 2.1 假设

- **H1.1**：把 `riskScore` 的三因子从「线性加权」升级为「带先验的贝叶斯更新」，
  在样本充足时能把「头号嫌疑的命中率」提升。
- **H1.2**：用生存分析里的 **at-risk 集（风险集）** 给每次崩溃的嫌疑排名做
  时间加权，能区分「刚更新的插件」与「更新了很久但一直命中的插件」。
- **H1.3**：引入**版本 diff 特征**（配置变更、依赖树变化）作为第四因子，
  比单纯「最近更新」有更高解释力。

### 2.2 实验设计

| 实验 | 方法 | 度量 | 判据 |
|---|---|---|---|
| E1.1a 基线 | 记录当前 `riskScore` 的嫌疑命中率 | 命中率、排名准确率（Top-1/Top-3） | 基线值 |
| E1.1b 贝叶斯 | 用 `Beta(1,1)` 先验 + 每次崩溃的命中/未命中做更新 | 同上 | 命中率提升 ≥ 5% 且误伤率不升 |
| E1.2 | 生存分析 at-risk 加权排名 | 排名准确率 | Top-1 提升 ≥ 3% |
| E1.3 | 版本 diff 特征消融 | 特征重要性 | diff 特征贡献 ≥ 10% |

### 2.3 风险与缓解

| 风险 | 缓解 |
|---|---|
| 样本稀疏（真实崩溃事件少） | 用合成崩溃序列做离线回放 + 小样本时保持现有逻辑（`Metric.defined`） |
| 过拟合到本机 | 特征在 `tests/unit/` 用契约测试钉住，禁止只在单设备绿 |
| 与现有风险评分行为不兼容 | 新模型作为**并行读数**上线，面板同时显示两套，不切换默认值 |

### 2.4 落地位置

- `src/lifecycle.ts` 的 `riskScore`（保留为 fallback）
- 新文件 `src/risk-bayes.ts`（一个数学模型一个文件）
- `src/observability.ts` 增加 `riskCalibration` 指标
- `tests/unit/risk-bayes.test.ts`

## 3. RQ2 · 误伤更少：风险校准与置信

### 3.1 假设

- **H2.1**：当前 `confirmRounds=2` 的阈值在「偶发崩溃」场景下仍会误伤。
- **H2.2**：给 `confirmRounds` 加上**基于置信度**的自适应阈值（样本少时更保守），
  能在保持检出率的同时降低误伤。
- **H2.3**：引入「误伤反馈」闭环——用户手动 reenable 成功即视为「误伤样本」，
  用于校准模型。

### 3.2 实验设计

| 实验 | 方法 | 度量 | 判据 |
|---|---|---|---|
| E2.1 | 统计历史 `reenable` 事件中的「误伤」占比 | 误伤率 | 基线值 |
| E2.2 | 自适应阈值模拟 | 误伤率 / 检出率 | 误伤率降 ≥ 20% 且检出率不降 |
| E2.3 | 误伤反馈接入 | 校准前后误伤率 | 3 个月内误伤率下降 |

### 3.3 关键设计：诚实边界

- 误伤率与检出率都走 `Metric<T>`，样本不足时 `defined:false`。
- 自适应阈值**必须可解释**（面板显示「本轮为何提高阈值」），不做黑盒。
- 误伤反馈要**区分「用户主动放行」与「系统自动恢复」**——前者是证据，后者不是。

### 3.4 落地位置

- `src/recovery-policy.ts` 的 `confirmRounds` 逻辑
- 新增 `src/risk-calibration.ts`
- `tests/unit/recovery-policy.test.ts` 扩展
- 面板新增「误伤反馈」卡片（`InsightCards.tsx`）

## 4. RQ3 · 信号更早：预防性健康指标

### 4.1 假设

- **H3.1**：插件**启动耗时**与**加载错误**的早期分布变化，能在崩溃前预警。
- **H3.2**：`plugin-manager/changed` 事件 + 配置 diff 的组合，比单纯等崩溃更早暴露风险。
- **H3.3**：异常终止通道（`abnormal-boot.ts`）的**计数趋势**本身是前兆信号。

### 4.2 实验设计

| 实验 | 方法 | 度量 | 判据 |
|---|---|---|---|
| E3.1 | 采集插件加载耗时分布，做 EWMA + 控制带 | 预警提前量（崩溃前多少轮） | ≥ 1 轮 |
| E3.2 | 配置 diff 的「变更频率」做 CUSUM | 提前量 | ≥ 1 轮 |
| E3.3 | 异常终止计数的趋势回归 | 提前量 | ≥ 1 轮 |

### 4.3 关键设计：不夸大

- 预防性指标**只预警，不行动**——行动仍走 RQ1/RQ2 的取证流程。
- 预警必须带**诚实边界**：样本不足不预警，绝不「宁可错杀」。
- 预警与确认**解耦**：预警是 `Metric`，确认是状态机 `deciding`。

### 4.4 落地位置

- `src/observability.ts` 增加 `loadTimeEwma` / `configChangeCusum`
- `src/lifecycle.ts` 增加预警阶段（或独立 `alerting` 维度）
- `tests/unit/observability-math.test.ts`

## 5. RQ4 · 验证更硬：可证伪的测试体系

### 5.1 假设

- **H4.1**：高频变异子自动化后，能持续捕获「看起来绿」的假绿。
- **H4.2**：故障注入（主动注入坏插件）能发现单元测试覆盖不到的时序缺陷。
- **H4.3**：跨工作区回归能发现隔离串扰（`decision.ts` 已知的指针串扰）。

### 5.2 实验设计

| 实验 | 方法 | 度量 | 判据 |
|---|---|---|---|
| E4.1 | 实现变异子工具（删除 try/catch、交换比较、移除 phase、改指针路径） | 变异杀灭率 | ≥ 80% |
| E4.2 | 沙箱 profile 注入坏插件，跑守护矩阵 | 检出率 | 100% |
| E4.3 | 多分区并行跑同一测试矩阵 | 隔离违例数 | 0 |

### 5.3 落地位置

- `scripts/mutation.mjs`（变异工具）
- `tests/fault-injection/**`（故障注入）
- `.cycles/verify/` 增加回归清单

### 5.4 风险

| 风险 | 缓解 |
|---|---|
| 变异测试拖慢 CI | 变异子只对 `src/` 纯函数层跑，限时 |
| 故障注入破坏沙箱 | 只在独立沙箱 profile（`sb-rg-*`）跑，绝不碰主力 profile |

## 6. 迭代节奏（对齐 macro_cycle）

```
plan → design → build → test → deploy → maintain
```

每个 RQ 走完整六阶段，门禁 G0–G3 全部通过才进入下一个 RQ。

| 阶段 | 交付物 | 门禁 |
|---|---|---|
| plan | 假设 + 实验设计（本文档的对应章节） | E1 意图对齐 |
| design | 模块设计 + 契约清单 | E2 规格符合 |
| build | 源码 + 注释（为什么这样写） | — |
| test | 四层测试 + 变异自证 + 性能基线 | G2 测试零错误 |
| deploy | 沙箱验证 + 文档更新（README） | G3 构建零失败 |
| maintain | `.cycles/` 记录 + 技术债登记 | E8 回归完整性 |

## 7. 度量体系（如何知道变好了）

### 7.1 核心指标（写进 `.cycles/config.yml` 的 `control_bands`）

| 指标 | 定义 | 目标 |
|---|---|---|
| 崩溃检出率 | `detected / crashes` | 提升 |
| 误伤率 | 误关插件数 / 总关闭数 | 下降 ≥ 20% |
| 恢复成功率 | 稳定启动数 / 恢复尝试数 | 提升 |
| 检测延迟 | 从崩溃到决策的轮数 | 下降 |
| 复杂度 | band-detector 计分 | ≤ 100 |

### 7.2 度量纪律

- 所有指标走 `Metric<T>`，不可判定时 `null`，绝不当 0。
- 指标必须带 `formula/inputs/sampleSize/confidence`。
- 指标在面板可见（白盒），不做后台黑盒。

## 10. 本文档自身的验证

本文档的每一个「落点」都必须在对应源码文件里存在。读者可用以下方式抽查：

```bash
# 抽查引用真实性
grep -n "function guardExpression" src/decision.ts
grep -n "function riskScore" src/lifecycle.ts
grep -n "function markovAnalysis" src/markov.ts
grep -n "function intervalSurvival" src/survival.ts
grep -n "function controlBand" src/control-band.ts
grep -n "const ALLOWED" src/lifecycle.ts
grep -n "function projectKey" src/isolation.ts
grep -n "function computeRevision" src/change-guard.ts
```

**如果某行不存在**，说明本文档与代码漂移——这是**最需要修的**问题，
因为一份与代码不符的研究文档比没有文档更危险。

## 11. 结语：这套计划的三个自检

1. **每个假设能被证伪吗？**——不能证伪的假设不进 plan 阶段。
2. **每个度量能走 `Metric<T>` 吗？**——不能走的，先解决度量再谈优化。
3. **每个落点能 grep 到吗？**——不能 grep 到的，是愿望不是计划。

这套研究文档的目的，是让 `dsh-recency-guard` 从一个「会修崩溃的插件」，
变成一个**「知道自己为什么对、也知道自己在什么情况下会错」的可证伪系统**。
