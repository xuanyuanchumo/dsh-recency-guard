# 03 · 数据结构与算法选型

> 目的：本项目大量「为什么不用更流行的做法」的判断，都写在源码注释里。本篇把它们汇总成
> 一张选型账：**选了什么、为什么、放弃的备选、复杂度、失效条件**。
>
> 纪律：复杂度写不出来或写错，下一个维护者就会「优化」错方向。

## 0. 选型四条元规则

1. **确定性优先**——同样的输入必须得到同样的输出，否则白盒审计无从谈起。
2. **小数据用精确算法**——本项目典型规模是「几十个插件、几十个能力、≤50 个间隔」。
   为这个规模上流式/近似算法，是给可审计性制造麻烦。
3. **崩溃路径必须同步且短**——崩溃时进程随时会死，异步和长循环都等于「什么都没留下」。
4. **结构要自描述**——长度前缀、`phase` 字段、schemaVersion，都是为了让「读到半成品」
   能被识别而不是被误读。

## 1. 环形缓冲 `RingBuffer`

| 项 | 内容 |
|---|---|
| 用途 | 只关心最近 W 个观测（启动序列、迁移历史、步骤区间）的窗口统计 |
| 数据结构 | 定长数组 + 头尾指针（或直接 `shift()` 截断） |
| 复杂度 | push O(1) 摊销，内存 O(W) |
| 落点 | `lifecycle.ts`（`historyLimit=200`、`REJECTED_LIMIT=50`、`STEP_LIMIT=120`）、`observability.ts` |
| 验证 | `tests/unit/observability-math.test.ts` |

**为什么不用无限数组**：观测面不能无限增长——面板每 5s 轮询一次，
日志上限 1000 条（`readJournal(1000)` 封顶），长期运行后每次启动都要解析几 MB 文件。

**边界**：环形缓冲会让「最早」的观测被丢弃。对「趋势」类指标，需要明确说明窗口大小，
否则用户会以为看到了全量历史。

## 2. Top-K 排序：全量排序 vs 最小堆

| 项 | 内容 |
|---|---|
| 用途 | 嫌疑/危险率排名，面板要逐行显示**完整**排名 |
| 选定 | **全量排序** O(n log n)（`rankHazards` / `rankByRecency`） |
| 备选 | 大小为 k 的最小堆 O(n log k) |
| 为什么 | 堆只给出前 k 个，面板要完整排名还得再排一次；n ≤ 100 时全量排序更快且保序稳定 |
| 何时换 | 插件规模真的上千时，换最小堆 |

**关键判断**：选型的依据是**使用方式**（完整展示），不是渐近复杂度。
这是本篇最想传达的一条：**复杂度分析要结合消费端**。

---

## 3. 分位数：精确排序 + 线性插值 vs P²

| 项 | 内容 |
|---|---|
| 选定 | 精确排序 + 线性插值 O(n log n)，与 NumPy `linear` 一致 |
| 备选 | P²（滑动 percentile estimation）近似算法 |
| 为什么 | P² 是为「流式、n 很大、内存受限」设计的；本模块 n ≤ 50，精确值更可审计（契约测试逐字节比对） |
| 边界 | 线性插值在 n=1 时退化为唯一值；n=0 时不可判定 |

---

## 4. 能力图：邻接表 + Set 语义 + 双向可达性

`src/capability.ts` 把能力建模成**有向图**：`capability --produces--> fact <--consumes-- capability`。

| 项 | 内容 |
|---|---|
| 选定 | **邻接表**：`Map<id, CapabilityRecord>` + 记录内的 id 数组 |
| 备选 | 邻接矩阵 |
| 为什么 | 能力数在几十量级，矩阵是 O(n²) 空间且稀疏，邻接表是 O(n+m) |
| 消费者/生产者 | **Set 语义**（数组去重）而非数组——同一能力被多处消费是常态 |
| 插入序 | 由 `Map` 保证，投影输出稳定可比对 |
| 关系数组 | `upsert` 时**引用拷贝**，调用方之后修改自己的数组不影响索引 |

**双向可达性分析的三种缺口**（`analyze()`）：

| 缺口 | 定义 | 含义 |
|---|---|---|
| 过度生产 | 产出无人消费 | 白盒可见的浪费 |
| 消费断链 | 消费无人生产 | 功能不连通 |
| 注册面缺口 | 声明了却没被实例化 | 能力写在空气上 |

**命名纪律**：`consumes` = 我消费谁；`consumedBy` = 谁消费我。
旧字段名 `consumers/producers` 方向相反，是真实的可读性缺陷，已实测修正。

**契约**：`capability-specs.ts:445 verifyCapabilityContract` 做**双向比对**——
索引是投影，真相在注册处，漏一条就是真缺口。

## 5. 连通分量：并查集（弱连通）

| 项 | 内容 |
|---|---|
| 用途 | 图谱中识别「孤岛」节点（无连接） |
| 选定 | **弱连通分量**（并查集） |
| 为什么不用强连通 | 用户关心的是「这个节点与系统有没有关系」，而不是「能不能回溯到自己」；
  能力图本身是 DAG，强连通分量会退化为单点，没有信息量 |
| 复杂度 | O(V + E)（近似） |
| 落点 | `graph-data.ts:286 connectedComponents`（`union` 在 :304） |

**孤立判定的坑**：`graph-model.ts:300` 注释提到「写过两次实测债注释」——
孤立节点若不计入分量，会出现「点了没反应」的假交互。

---

## 6. 布局：分层布局 vs 力导向

| 项 | 内容 |
|---|---|
| 选定 | **分层布局**（列 = 生命周期阶段），`layered` + 可选 `radial` |
| 备选 | 力导向（force-directed） |
| 为什么 | 能力图是**有向无环**，分层直接对应语义；力导向在 20~60 节点抖动且**不可复现** |
| 复杂度 | O(V + E) 分层；力导向 O(iterations × V²) |
| 落点 | `graph-model.ts:570 layoutPositionsOf`、`graph-data.ts:195 layoutGraph` |

**确定性是不可审计性的反面**：白盒要求「同样的数据两次渲染位置相同，可逐字节比对」。
力导向的随机初值会让「为什么这个节点在这里」无法回答。

**环形布局** `radialPositions` 是第二模式，用于「只看关联、按阶段分圈」的视图。

## 7. 命中测试：哈希网格 vs 线性扫描

| 项 | 内容 |
|---|---|
| 用途 | 图谱上点选/悬停的节点查找 |
| 选定 | **哈希网格**（空间哈希，`cellSize=120`） |
| 备选 | 线性扫描 O(N) |
| 为什么 | 节点数十~数百时，网格是 O(1) 查询且实现只有二十行；线性扫描每帧都要跑 |
| 复杂度 | 构建 O(N)，查询 O(单元格内节点数) |
| 落点 | `viewport.ts:239 SpatialGrid` |
| 验证 | `performance-baseline.md`：200 节点命中测试 ≤ 0.05 ms |

**边界**：`cellSize` 是魔法数。节点尺寸差异大时，会出现「大节点跨格，点击落在空隙」。
本项目用 `HIT_TOLERANCE = 6` 兜底，并在 `hitNodesOf` 里做精确几何判定。

## 8. 分区键：路径归一 + SHA-256 前 16 位

| 项 | 内容 |
|---|---|
| 用途 | 多工作区隔离，同一守护插件并存互不污染 |
| 选定 | 规范化路径 → SHA-256 → 前 16 hex（64 bit） |
| 为什么不用路径编码 | 路径可能含中文、盘符、`..`，编码后不可读且可能超长；哈希定长、无字符集问题、不泄露路径 |
| 可读性 | 由「分区索引」里的 `label` 字段补回 |
| 归一化 | 分隔符统一 `/`、盘符小写、解析 `.`/`..`、去尾分隔符 |
| 落点 | `isolation.ts:60 normalizeWorkspace`、`:92 projectKey` |

**为什么要折叠盘符大小写**：Windows 路径大小写不敏感，`D:/Project/Alpha` 与
`d:/project/alpha` 是同一目录。不折叠就会**同一项目被拆成两份记忆**。

**碰撞概率**：64 bit，几十个项目绰绰有余。若未来项目数上万，应加长到 32 hex。

## 9. 原子写与失效锁自愈

| 项 | 内容 |
|---|---|
| 用途 | 崩溃路径上写状态文件不能留下半成品 |
| 选定 | `dsh-atomic-write` 的原子写（临时文件 + rename） + 锁超时 |
| 失效锁判据 | 锁内容为空 / 非正整数 PID / PID 对应进程已死，且文件年龄 > 5s |
| 为什么年龄 > 5s | 避开锁创建与写 PID 之间的零字节窗口，**绝不抢活锁** |
| 落点 | `store.ts` 的 `Store.init` 与 `updateState` |

**真实事故**：崩溃恰好发生在锁创建与写 PID 之间，遗留 0 字节 `state.json.lock`，
此后每次启动都等满超时并致命。修复后启动不再抛出（`boot()` 失败降级留痕，不再 rethrow）。

**为什么守护的启动绝不能抛出**：一个可恢复的写锁超时会把宿主变成
`dsh: fatal load failure`（退出码 1）。观测/恢复设施不能拖垮主流程。

## 10. 指针文件：表达式作用域的桥

| 项 | 内容 |
|---|---|
| 问题 | 守护行的 `disabled` 表达式运行在 `with (ctx) { eval(expr) }`，有 `ctx` 和 `process`，
**没有 require**；它能拿到 `profileContext.dir`，但拿不到分区键 |
| 选定 | profile 目录下放 `.recency-guard/current.json`（指针），指向当前分区的决策文件 |
| 为什么不用表达式枚举分区 | 在无 require 作用域里读目录、逐个解析 JSON 既不可靠又慢 |
| 为什么宁可误指不指不到 | 指不到 ⇒ 全部放行 ⇒ 崩溃重演（破坏恢复能力）；误指 ⇒ 只多关一个可能无关的插件 |
| 失败语义 | 指针缺失/不合法 ⇒ 表达式返回 `false`（放行） |
| 落点 | `decision.ts:105 writePointer`、`:139 guardExpression` |

**诚实边界**：指针在 profile 目录是**全局一份**，并发工作区会串扰。这是已知取舍，
因为 DSH profile 本身是单实例资源。

## 11. 两阶段提交 + 重启对账

| 项 | 内容 |
|---|---|
| 目的 | 崩溃打断时不留半成品状态 |
| 阶段 1 | `prepared`：决策文件写好、嫌疑名单落 journal，但 `disable` 名单标记 `phase: 'prepared'` |
| 阶段 2 | `quarantined`：`pluginManager` 确认关闭成功后升级 |
| 对账 | 下次启动按磁盘现状 reconcile（confirmed / reverted） |
| 为什么同文件 | 决策文件是守护行表达式的唯一输入；`phase` 字段给 reconcile 与面板看 |
| 落点 | `recovery-policy.ts:133 DecisionPhase`（reconcile 在 :260 `reconcilePrepared`） |

**为什么不用两个文件**：两个文件会引入「哪个为准」的歧义。单一文件 + `phase` 字段
让**真相只有一份**。

## 12. 乐观并发：哈希 revision vs 计数器

| 项 | 内容 |
|---|---|
| 问题 | 面板每 5s 轮询快照，用户可能按着过期地图操作 |
| 选定 | 快照带 `revision`（事实派生的 12 hex 哈希），动作带 `expectedRevision` |
| 为什么哈希 | 计数器需要单调持久位点，崩溃时会落后于状态 ⇒ 假冲突/假放行；哈希从事实本身派生，
崩溃重启后同一份事实必得同一枚 ⇒ 幂等 |
| 编码 | 列表用**长度前缀** `${byteLength}:${s}`，避免 `join(',')` 的边界歧义 |
| 语义 | 不带 ⇒ 放行但标记 `unchecked`；带了且相等 ⇒ ok；带了不等 ⇒ `stale`（409，动作不执行） |
| 落点 | `change-guard.ts:68 computeRevision`、`:98 checkRevision` |

**为什么保留 `autoDisabled` 原序**：顺序本身是因果信息（先关谁）。
排序会把「A 先 B 后」与「B 先 A 后」折叠成同一枚 revision——把两种事实当成一种。

**48 bit 够吗**：冲突判定要的是「变了没有」，不是抗对抗性碰撞，48 bit 足够。

## 13. 事件驱动 + 启动兜底：双源真相

| 项 | 内容 |
|---|---|
| 主源 | 订阅宿主 `plugin-manager/changed`（500ms 防抖） |
| 兜底 | 每次启动的同步 diff（journal vs 当前安装版本） |
| 为什么双源 | CLI / 手工编辑不发 `plugin-manager/changed` 事件；GUI/工具路径则立即进时间线 |
| 事件定位 | **加速器，不是唯一真相** |
| 落点 | `event-watch.ts`、`recency.ts:171 diffVersions` |

**为什么不做高频轮询**：mtime 扫描是启动路径最贵动作，绝不进定时器。
变更检测只跑启动时 + 事件触发。

## 14. 同步 IO vs 异步：崩溃路径的时序纪律

| 路径 | 选择 | 理由 |
|---|---|---|
| 守护行安装 | **同步** | 异步会输给崩溃（Loader 并发求值竞态） |
| 启动记录 / 哨兵 / 决策发布 | **同步** | 进程随时会死，异步等于没记 |
| 状态机迁移 | 异步（boot） | 崩溃决策本身同步，但启动编排可异步 |
| 自动恢复 | 延后到 HMR 事务之外（boot 后 1.5s，定时器 unref） | Loader 自身可能正处在事务中，会报 `HMR transactions cannot be nested` |

**代价**：启动时多几次同步 IO。用「只装一次、之后幂等跳过」把重复成本降到一次 patch 读取。
`performance-baseline.md` 把「`apply()` 内同步 IO 次数 ≤ 6」列为硬阈值。

## 15. 复杂度预算与「一个模型一个文件」

| 项 | 内容 |
|---|---|
| 预算 | `complexity_budget: 100`（band-detector 计分） |
| 计分范围 | 只算 `src/` 自写源码；排除 `lib/`、`runtime/`、`node_modules/`、`.tmp/`、`.cycles/`、`tests/` |
| 拆分案例 | `patch.ts` 142 → 三层；`observability.ts` → `survival.ts` / `control-band.ts`；`index.ts` → `abnormal-boot.ts` |
| 拆分原则 | 一个数学模型一个文件，单测与实现同址 |

**为什么排除第三方**：否则 band-detector 会把 esbuild 产物与宿主解出的运行时
一起计分——那是**用别人的代码罚我们的分**。

## 16. 选型速查表

| 问题 | 选定 | 放弃 | 依据 |
|---|---|---|---|
| 窗口统计 | 环形缓冲 | 无限数组 | 观测面有界 |
| 完整排名 | 全量排序 | 最小堆 | 消费端要全量 |
| 分位数 | 精确 + 插值 | P² | n≤50，可审计 |
| 能力关系 | 邻接表 + Set | 矩阵 | O(n+m)，稀疏 |
| 连通性 | 并查集（弱） | 强连通 | 能力图是 DAG |
| 布局 | 分层 + 径向 | 力导向 | 确定性 |
| 命中测试 | 哈希网格 | 线性扫描 | O(1) 查询 |
| 分区键 | SHA-256/16 | 路径编码 | 定长、无字符集问题 |
| 并发控制 | 事实哈希 revision | 计数器 | 幂等、抗崩溃 |
| 列表编码 | 长度前缀 | `join(',')` | 自描述、无歧义 |
| 变更检测 | 事件 + 启动 diff | 高频轮询 | 事件是加速器不是真相 |
